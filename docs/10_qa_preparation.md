## 🧠 Technical Questions

---

### Q: What if the LLM misinterprets the diagnosis?

**Answer:**
> "Great question. The LLM is not trusted for code generation — it's only used to extract clinical entities like diagnosis text and severity. That extraction is then validated by our Pydantic schema. If the structured output doesn't conform, the pipeline returns an error rather than proceeding with bad data. The actual ICD code is never generated by the LLM — it's selected deterministically from our internal validated database using semantic similarity search. So even if the LLM's extraction is slightly off, the mapping engine only returns codes that exist in our DB and are validated as billable."

---

### Q: How do you handle ICD-10 code updates every year?

**Answer:**
> "We designed our ICD table with a version field, and we use Alembic for schema migrations. Updating the ICD dataset is a versioned database migration operation — new codes are inserted, deprecated codes are flagged inactive. The system never uses hard-coded code lists in the application layer. This means updates are controlled, traceable, and safe. For production, this would be automated annually using the CMS published ICD-10-CM release."

---

### Q: How scalable is your architecture?

**Answer:**
> "The architecture is horizontally scalable by design. FastAPI supports async operations and can be scaled with multiple workers behind a load balancer. LangGraph workflows can be routed through a task queue like Celery with Redis for high-volume processing. PostgreSQL with pgvector handles large datasets with proper indexing — we've added IVFFlat index on embeddings for fast approximate nearest neighbor search. For enterprise scale, the DB can be moved to managed PostgreSQL like AWS RDS or Supabase."

---

### Q: What about HIPAA compliance?

**Answer:**
> "We've designed with PHI protection in mind. In our current POC, we store only a SHA-256 hash of the raw clinical text for audit purposes, not the full text. For production, we would implement: encryption at rest for all clinical data fields, TLS in transit, role-based access control with JWT, audit logging, and a Business Associate Agreement with cloud providers. We use Groq for LLM inference — in production, we'd evaluate a private deployment or an API provider with HIPAA BAA support. These are Phase 2 compliance considerations beyond the POC scope."

---

### Q: Can the system generate wrong codes?

**Answer:**
> "No — and this is one of our core design principles. The system cannot generate an ICD code that doesn't exist in our internal database. The LLM cannot create codes — it only extracts clinical text. The mapping engine then does a semantic search against our validated ICD-10 dataset and applies a billable status check. If no code passes validation, the system returns a 'no confident match' response rather than guessing. Explainability is built-in: every suggestion includes the supporting evidence text from the clinical document."

---

### Q: How is this different from just calling ChatGPT?

**Answer:**
> "Calling ChatGPT would give you ICD codes generated from model weights — with no guarantee the code exists, is billable, is current, or is based on actual clinical evidence. Our system is fundamentally different: LLM is used only for clinical entity extraction. Code selection is deterministic and database-backed. Every code is validated against billable status. Every suggestion includes supporting evidence. We also have an audit comparison layer and revenue delta calculation — that doesn't exist in any generic LLM."

---

### Q: What is LangGraph and why did you use it?

**Answer:**
> "LangGraph is a graph-based orchestration framework for multi-agent workflows built on top of LangChain. We chose it over simple LangChain chains because our workflow is non-linear — it has conditional routing. Specifically, the audit comparison path only activates when a human ICD code is provided. LangGraph gives us stateful execution, where each agent reads from and writes to a shared CodingState object. This makes the workflow predictable, debuggable, and extensible. Adding a new agent node is a clean operation without disrupting existing logic."

---

### Q: How do you calculate revenue delta?

**Answer:**
> "We maintain a revenue lookup table with simulated reimbursement values per ICD code, modeled after DRG-based reimbursement logic. When we compare the AI-suggested code and the human-entered code, we look up both reimbursement values and compute the delta. For example, if the human coded E11.9 at $2,100 reimbursement, but the AI identifies E11.22 — which captures a CC comorbidity — at $2,550, the delta is $450. This demonstrates the financial impact of specificity improvement. In production, this would integrate with the actual DRG grouper engine and payer contract tables."

---

### Q: Why did you choose Groq over OpenAI?

**Answer:**
> "Groq provides extremely low-latency LLM inference, which matters for our demo and for production use cases where multiple documents might be processed. We're using it for the clinical extraction step, where speed matters. That said, our architecture is model-agnostic — the LLM call is abstracted, so we can swap to OpenAI, Anthropic, or a private model deployment without changing other system components. Groq was the pragmatic choice for POC velocity."

---

### Q: What is your ICD dataset based on?

**Answer:**
> "We use a curated subset of the official ICD-10-CM dataset published by the Centers for Medicare & Medicaid Services (CMS). For this POC, we've selected approximately 500 high-frequency codes across key clinical categories including diabetes, cardiovascular, sepsis, renal, and respiratory. Each code includes the official description, billable status, and CC/MCC flag. The full 70,000+ code set would be an import operation for production."

## 🏆 Business Impact Questions

---

### Q: What's the actual ROI for a hospital?

**Answer:**
> "Studies show hospitals miss 2–8% of potential reimbursement due to under-coding, primarily from missed CC/MCC capture and non-specific diagnosis codes. For a mid-size hospital with $100 million in annual claims, that's $2–8 million in recoverable revenue. Our system can identify these gaps systematically at scale, with audit trails and explainability that support compliance review. That's the core business case."

---

### Q: Who would use this in a hospital?

**Answer:**
> "The primary users are medical coding specialists and HIM (Health Information Management) departments. They use our system in audit mode — they enter their coded output, and the system cross-checks it against the AI suggestion and flags discrepancies for review. The second use case is real-time coding assistance where coders see the AI suggestion before finalizing their code assignment. Management uses the dashboard to track systemic under-coding patterns and revenue leakage trends."

---

### Q: What makes this better than existing coding tools?

**Answer:**
> "Most existing AI coding tools use LLM generation directly — high risk of hallucinated codes, no audit layer, no revenue simulation. Our approach is unique in three ways: one, deterministic DB-backed mapping with zero hallucination risk; two, explainable audit comparison that shows exactly what the human missed and why; three, financial intelligence that quantifies the revenue impact of each discrepancy. That combination doesn't exist in current market tools."
